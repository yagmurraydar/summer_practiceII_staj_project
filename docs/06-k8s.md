# Kubernetes

## 1. Kubernetes Nedir?

Kubernetes, container'lı uygulamaları yönetmek ve orkestre etmek için kullanılan bir platformdur.

Docker tek başına container oluşturma ve çalıştırma işlemlerini sağlar. Kubernetes ise birden fazla container'ın veya uygulamanın istenen durumda çalışmasını, yeniden başlatılmasını, ağ üzerinden birbirleriyle iletişim kurmasını ve güncellenmesini yönetir.

Bu projede Docker Compose ile çalışan FastAPI ve PostgreSQL uygulaması Kubernetes ortamına taşınmıştır.

---

## 2. Kullanılan Ortam

Kubernetes cluster'ı local ortamda `kind` kullanılarak oluşturuldu.

Cluster içerisindeki node:

```text
kind-control-plane
```

Kubernetes ile iletişim kurmak için `kubectl` kullanıldı.

Cluster kontrolü için:

```bash
kubectl get nodes
```

komutu kullanıldı.

### kind Nedir?

`kind` (Kubernetes IN Docker), Kubernetes cluster'ını Docker container'ları içerisinde oluşturmaya yarayan bir araçtır.

Bu projedeki yapı şu şekildedir:

```text
Ubuntu
  │
  ▼
Docker
  │
  ▼
kind-control-plane
  │
  ▼
Kubernetes Cluster
```

---

## 3. kubectl Nedir?

`kubectl`, Kubernetes cluster'ı ile iletişim kurmak ve Kubernetes kaynaklarını yönetmek için kullanılan komut satırı aracıdır.

Örneğin:

```bash
kubectl get pods
```

komutu Kubernetes cluster'ındaki Pod'ları listeler.

Bir YAML dosyasını oluşturmak veya güncellemek için:

```bash
kubectl apply -f deployment.yaml
```

komutu kullanılır.

Bu komut Kubernetes'e YAML dosyasında tanımlanan istenen durumu uygular.

---

## 4. Pod Nedir?

Pod, Kubernetes'in temel çalışma birimidir.

Kubernetes doğrudan tek bir container'ı değil, Pod adı verilen yapıyı yönetir. Bir Pod içerisinde bir veya birden fazla container bulunabilir.

Bu projede API ve PostgreSQL ayrı Pod'larda çalıştırıldı.

Pod'ları görüntülemek için:

```bash
kubectl get pods
```

komutu kullanıldı.

Mimari:

```text
API Pod
└── FastAPI Container

PostgreSQL Pod
└── PostgreSQL Container
```

---

## 5. Deployment Nedir?

Deployment, Pod'ların yönetilmesini sağlayan Kubernetes kaynağıdır.

Pod'u doğrudan oluşturmak yerine Deployment kullanmak daha kullanışlıdır çünkü Deployment istenen sayıda Pod'un çalışmasını sağlar.

Örneğin:

```yaml
replicas: 1
```

ifadesi:

> Uygulamadan her zaman bir adet çalışan Pod bulunmasını istiyorum.

anlamına gelir.

Bir Pod silinir veya hata nedeniyle kapanırsa Kubernetes, Deployment'ın tanımladığı istenen duruma ulaşmak için yeni bir Pod oluşturabilir.

Bu projede hem FastAPI hem de PostgreSQL için Deployment kullanıldı.

---

## 6. Labels ve Selectors

Kubernetes'te kaynakların birbirini bulabilmesi için label ve selector yapıları kullanılır.

Örneğin API Deployment'ında:

```yaml
selector:
  matchLabels:
    app: task-manager-api
```

ve Pod şablonunda:

```yaml
labels:
  app: task-manager-api
```

kullanıldı.

Buradaki mantık:

```text
Deployment
    │
    │ app=task-manager-api
    ▼
API Pod
    │
    └── app=task-manager-api
```

şeklindedir.

Deployment, bu label sayesinde hangi Pod'ların kendisine ait olduğunu bilir.

Service'ler de aynı mantıkla hangi Pod'lara trafik göndereceğini belirler.

---

## 7. Docker Image ve kind

FastAPI uygulaması önce Docker image'ı haline getirildi.

İlk image:

```bash
docker build -t task-manager-api:latest .
```

komutu ile oluşturuldu.

Ancak Kubernetes cluster'ı doğrudan bilgisayarın Docker ortamında değil, `kind-control-plane` isimli kind node'u içerisinde çalışıyordu.

Bu nedenle local Docker ortamındaki image'ın Kubernetes node'una aktarılması gerekti.

Bunun için:

```bash
kind load docker-image task-manager-api:latest
```

komutu kullanıldı.

Mantık şu şekildedir:

```text
Local Docker
      │
      │ task-manager-api image
      ▼
kind-control-plane
      │
      ▼
Kubernetes Pod
```

Daha sonra uygulamanın yeni sürümü için:

```bash
docker build -t task-manager-api:v2 .
```

komutu ile yeni image oluşturuldu ve:

```bash
kind load docker-image task-manager-api:v2
```

komutu ile kind node'una aktarıldı.

---

## 8. imagePullPolicy: Never

Local kind ortamında image'ın internetten veya bir container registry'den çekilmesini istemedik.

Bu nedenle bazı Deployment tanımlarında:

```yaml
imagePullPolicy: Never
```

kullanıldı.

Bu ayarın anlamı:

> Kubernetes image'ı dışarıdan çekmeye çalışma, node üzerinde bulunan image'ı kullan.

Ancak bunun çalışabilmesi için image'ın önceden kind node'una yüklenmiş olması gerekir.

Image node üzerinde yoksa `ErrImageNeverPull` hatası oluşabilir.

---

## 9. Service Nedir?

Pod'ların IP adresleri kalıcı değildir.

Bir Pod silinip yeniden oluşturulduğunda IP adresi değişebilir. Bu nedenle başka bir uygulamanın doğrudan Pod IP'sine bağlanması doğru bir yöntem değildir.

Service, Pod'lara sabit bir erişim noktası sağlar.

Service:

* Belirli label'a sahip Pod'ları bulur.
* Trafiği bu Pod'lara yönlendirir.
* Pod değişse bile sabit bir erişim adı sağlar.
* Kubernetes içerisindeki uygulamaların birbirleriyle iletişim kurmasını kolaylaştırır.

Bu projede iki Service oluşturuldu:

```text
postgres
task-manager-api
```

---

## 10. PostgreSQL Service ve ClusterIP

PostgreSQL için `ClusterIP` türünde bir Service oluşturuldu.

Mimari:

```text
API Pod
   │
   │ postgres:5432
   ▼
PostgreSQL Service
   │
   ▼
PostgreSQL Pod
```

API, PostgreSQL'e doğrudan Pod IP'si ile bağlanmaz.

Bunun yerine:

```text
postgres:5432
```

adresini kullanır.

Buradaki `postgres`, PostgreSQL Service'inin adıdır.

Kubernetes'in DNS sistemi bu ismi otomatik olarak ilgili Service'e çözer.

`ClusterIP`, Service'in yalnızca Kubernetes cluster'ı içerisinden erişilebilir olmasını sağlar.

PostgreSQL için ClusterIP kullanılmasının nedeni veritabanını doğrudan dış dünyaya açmak istemememizdir.

---

## 11. API Service ve NodePort

FastAPI uygulaması için `NodePort` türünde bir Service oluşturuldu.

Örneğin:

```text
8000:32723/TCP
```

şeklinde bir çıktı görüldü.

Burada:

* `8000`, Service'in uygulamaya yönlendirdiği porttur.
* `32723`, Kubernetes node'u üzerinden erişim için kullanılan NodePort'tur.

Mimari:

```text
Kullanıcı
   │
   ▼
NodePort
   │
   ▼
task-manager-api Service
   │
   ▼
API Pod
```

NodePort kullanmamızın amacı API'ye cluster dışından erişim sağlamaktı.

`kubectl get svc` komutu ile Service'ler kontrol edildi.

---

## 12. ConfigMap Nedir?

ConfigMap, hassas olmayan yapılandırma bilgilerini uygulama kodundan ayırmak için kullanılan Kubernetes kaynağıdır.

Bu projede PostgreSQL ile ilgili hassas olmayan bilgiler ConfigMap içerisinde tutuldu.

Örneğin:

```text
POSTGRES_USER
POSTGRES_DB
```

ConfigMap adı:

```text
postgres-config
```

olarak oluşturuldu.

ConfigMap'in amacı yapılandırma bilgilerini doğrudan uygulama koduna veya Deployment YAML dosyasına gömmemektir.

---

## 13. Secret Nedir?

Secret, parola, token veya API anahtarı gibi hassas bilgileri ayrı bir Kubernetes kaynağında tutmak için kullanılır.

Bu projede:

```text
POSTGRES_PASSWORD
DATABASE_URL
```

Secret içerisinde tutuldu.

Secret adı:

```text
postgres-secret
```

olarak oluşturuldu.

Şifreyi ConfigMap içerisinde tutmak yerine Secret içerisinde tutmamızın nedeni, hassas bilgileri normal yapılandırma bilgilerinden ayırmaktır.

### Önemli Not: Base64 Şifreleme Değildir

Kubernetes Secret değerleri çoğu durumda Base64 encoding ile saklanır.

Ancak:

```text
Base64 encoding ≠ Encryption
```

Base64 kolayca çözülebilir.

Bu nedenle Kubernetes Secret kullanmak, verinin otomatik olarak tamamen şifrelendiği anlamına gelmez.

Production ortamlarında ek olarak:

* RBAC
* Encryption at rest
* Secret management araçları

gibi güvenlik önlemleri kullanılabilir.

## 14. DATABASE_URL'in Koddan Çıkarılması

Başlangıçta PostgreSQL bağlantı bilgisi doğrudan `app.py` içerisinde bulunuyordu:

```python
DATABASE_URL = "postgresql://myuser:mysecurepassword@postgres:5432/mydatabase"
```

Bu yöntemin problemi şifrenin doğrudan kaynak kod içerisinde bulunmasıydı.

Bu durum özellikle kodun GitHub gibi bir platforma yüklenmesi durumunda güvenlik riski oluşturabilir.

Daha sonra kod şu şekilde değiştirildi:

```python
import os

DATABASE_URL = os.getenv("DATABASE_URL")
```

Artık uygulama `DATABASE_URL` değerini doğrudan kod içerisinden değil, environment variable olarak almaktadır.

Akış:

```text
Kubernetes Secret
       │
       ▼
DATABASE_URL environment variable
       │
       ▼
API Container
       │
       ▼
os.getenv("DATABASE_URL")
```

Bu sayede bağlantı bilgisi uygulama kodundan ayrılmış oldu.

## 15. ConfigMap ve Secret Ayrımı

Bu projede hassas olmayan bilgiler ConfigMap'e, hassas bilgiler ise Secret'a yerleştirildi.

```text
ConfigMap
├── POSTGRES_USER
└── POSTGRES_DB

Secret
├── POSTGRES_PASSWORD
└── DATABASE_URL
```

Burada `DATABASE_URL` içerisinde hem hassas hem de hassas olmayan bilgiler bulunmaktadır.

Örneğin:

```text
postgresql://myuser:mysecurepassword@postgres:5432/mydatabase
```

Bu URL içerisinde:

* `postgres`: host adı
* `5432`: port
* `mydatabase`: veritabanı adı
* `myuser`: kullanıcı adı
* `mysecurepassword`: parola

bulunur.

Biz çalışır bir yapı oluşturmak için `DATABASE_URL` değerini Secret içerisinde tuttuk. Ancak daha ayrıntılı bir yapılandırmada bağlantı bilgisinin hassas olmayan parçaları ConfigMap'ten, parola gibi hassas bilgiler ise Secret'tan alınarak uygulama içerisinde oluşturulabilir.

## 16. Rolling Update Nedir?

Rolling Update, çalışan uygulamanın yeni bir sürüme güncellenirken Pod'ların kontrollü şekilde değiştirilmesini sağlayan Kubernetes mekanizmasıdır.

Bu projede önce yeni bir image oluşturuldu:

```bash
docker build -t task-manager-api:v2 .
```

Ardından image kind node'una yüklendi:

```bash
kind load docker-image task-manager-api:v2
```

Son olarak Deployment'ın image sürümü değiştirildi:

```bash
kubectl set image deployment/task-manager-api api=task-manager-api:v2
```

Kubernetes Deployment'ın yeni istenen durumunu gördü ve API Pod'unu yeni image ile çalıştırdı.

Güncelleme sonrasında:

```bash
kubectl get pods
```

ve:

```bash
kubectl get deployment task-manager-api -o wide
```

komutları kullanılarak yeni Pod'un çalıştığı ve Deployment'ın `task-manager-api:v2` image'ını kullandığı doğrulandı.

---

## 17. Rolling Update ve Kesintisizlik

Kubernetes Rolling Update mekanizmasının temel amacı yeni Pod'ları kademeli olarak devreye alırken eski Pod'ları kontrollü şekilde kaldırmaktır.

Birden fazla replica kullanıldığında örneğin:

```yaml
replicas: 3
```

şeklinde bir yapı olsaydı:

```text
Eski Pod 1   Running
Eski Pod 2   Running
Eski Pod 3   Running
```

yerine yeni sürüm kademeli olarak oluşturulabilirdi.

Ancak bu projede:

```yaml
replicas: 1
```

kullanıldı.

Ayrıca güncelleme sırasında:

```bash
kubectl get pods -w
```

komutu kullanılmadı.

Bu nedenle Rolling Update işleminin tamamlandığı yeni Pod ve yeni image kontrol edilerek doğrulandı, ancak Pod değişim süreci canlı olarak izlenmedi.

## 20. Sonuç

Bu proje kapsamında Docker Compose ile çalışan FastAPI ve PostgreSQL uygulaması Kubernetes ortamına taşındı.

Uygulama iki temel bölümden oluşturuldu:

* FastAPI uygulaması
* PostgreSQL veritabanı

Her iki uygulama Kubernetes üzerinde Deployment ve Pod yapıları kullanılarak çalıştırıldı.

Uygulamaların birbirleriyle iletişim kurabilmesi için Service'ler oluşturuldu. PostgreSQL için yalnızca cluster içerisinden erişilebilen ClusterIP, API için ise dış erişim sağlamak amacıyla NodePort kullanıldı.

Yapılandırma bilgileri ConfigMap ve Secret kullanılarak uygulama kodundan ayrıldı. Hassas bilgiler Secret içerisinde tutuldu.

Son olarak API image'ı `v2` sürümüne güncellenerek Kubernetes Deployment mekanizması ile Rolling Update işlemi gerçekleştirildi.

Bu çalışma sayesinde Kubernetes'in temel bileşenleri olan:

* Cluster
* Node
* kubectl
* Pod
* Deployment
* Labels
* Selectors
* Service
* ClusterIP
* NodePort
* ConfigMap
* Secret
* Environment Variables
* Rolling Update

kavramları uygulamalı olarak öğrenildi.
